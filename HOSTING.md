# Connect GitHub Pages to the working app

The public starting page stays at https://setsam37.github.io/video-flashcards/.
Render runs the Google sign-in screen, private libraries, uploads, and video processing.
The browser navigates to Render after submitting the Pages form, so private APIs and media use first-party session cookies.
GitHub Pages cannot run Python, keep server secrets, or process videos.

The code supports hosting; preparing these files does not create a Render service or a Google OAuth client.
Keep the current unconnected entry page until the live checks below pass.

## Create the server and Google client

1. Sign in to [Render](https://dashboard.render.com), connect the `setsam37/video-flashcards` repository, and choose **New → Blueprint**. Use `render.yaml` from `main`.
2. Review the service and disk charges **before applying**. The template requests one `1c-2g` web service (1 CPU, 2 GB RAM) and a 10 GB persistent disk. [Current pricing](https://render.com/pricing) is shown during creation; OpenAI usage is a separate charge. A smaller paid service may suffice for light use but has not been load-tested. Free services cannot provide this persistent-disk setup.
3. Reserve the service's actual public HTTPS origin. No URL is preassigned by this repository. Hosted startup uses Render's `RENDER_EXTERNAL_URL`; `PUBLIC_APP_URL` can override it for a custom domain.
4. In [Google Cloud's Google Auth Platform](https://console.cloud.google.com/auth/overview), configure the consent screen and audience. For a testing application, add each invited account as a test user. Create a **Web application** OAuth client. Register the exact authorized redirect URI `https://YOUR-ACTUAL-SERVICE.onrender.com/auth/callback`. Use the actual origin from step 3. The Pages URL is not the OAuth callback.
5. Enter the following **privately in Render's environment settings**, not GitHub source, Pages variables, or chat:

   - `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` from Google.
   - `OPENAI_API_KEY` from your existing key or a separate project key with a usage budget.
   - `ALLOWED_EMAILS` as a JSON array, e.g. `["your-account@example.com"]`. Add invited addresses here and to Google's test audience. Matching is exact and case-insensitive.
   - `SESSION_SECRET` is generated by the Blueprint. Keep it stable across redeploys; rotation invalidates temporary sign-in cookies.

6. Leave `PUBLIC_SIGNUP=false`. The app can permit any verified Google email with `PUBLIC_SIGNUP=true`, but every user's processing would use the operator's OpenAI account. Google audience/publication settings must also permit those users. This is a small invited study app; there are no per-user billing limits or storage quotas.
7. Deploy. Authentication settings are mandatory in hosted mode; incomplete configuration stops startup. Service health is `/api/health`. The database, uploads, checkpoints, sessions, and temporary upload storage live under `/var/data`.

Google email is displayed and used for invitations. The verified Google account subject is the stable storage identity. Changing IP addresses does not change a library. Different accounts use separate databases and media directories. The local library is not automatically uploaded.

## Check the live app before connecting Pages

1. Open `/api/health`: expect HTTP 200 and only `{"status":"ok"}` while signed out.
2. Open `/api/lectures` while signed out: expect HTTP 401. `/docs` should be unavailable.
3. Sign in with an invited Google account. Import the sample YouTube video, wait for its syllabus, select one chapter, and generate cards. Check flip, supporting excerpts, timestamps, topic study, and custom mix.
4. YouTube may block caption access from a hosted server. If it does, attach matching SRT/VTT captions or upload an MP4/WebM file. Do not treat a queued or failed import as a completed lesson.
5. Test a second invited account: it should start empty and must not read the first account's lecture ID, video, or job. Sign out and confirm private APIs return 401. An uninvited account cannot enter.
6. Restart the service. Confirm the same account retains its lessons and uploads. Interrupted jobs become retryable; completed cards and checkpoints remain saved.
7. Check an actual uploaded video and flashcard generation before relying on hosted uploads. The upload limit is 1 GB per file. The 10 GB disk also holds multipart temporary files, extracted audio, transcripts, and checkpoints, so monitor free space and keep enough headroom. Long processing may take several minutes.

## Publish the connected Pages form

After those live checks pass:

1. In GitHub repository **Settings → Pages**, choose **GitHub Actions** as the build source. The existing site remains available while its replacement is built.
2. In **Settings → Secrets and variables → Actions → Variables**, set `RECALL_APP_URL` to the verified HTTPS server origin. This URL is public; do not put any credential here.
3. In **Actions → Publish connected Pages → Run workflow**, use `main` and enter the same origin as `backend_url`.
4. Open the Pages URL, paste a video, and select **Proceed to lesson**. Sign in if needed; the video should open in that account's library. Reload during/after the transition and confirm it creates only one lesson.

Subsequent `main` pushes rebuild Pages when `RECALL_APP_URL` is set. The workflow verifies that the server is healthy before replacing the site. Until configured, the Pages build retains its honest offline notice.

## Operating and backing up

One container supervises one API and one worker. If either process exits, the container exits. Shutdown reaches child processes, including FFmpeg; interrupted work is recovered as retryable. A fresh worker heartbeat and readable SQLite databases are required for healthy status. Keep one service instance; the SQLite disk is not a shared multi-instance database.

Each account lives in `/var/data/accounts/<hash-of-google-sub>/`, with `study.sqlite`, `media/`, and `jobs/`. The root `auth.sqlite` holds revocable session digests, CSRF values, and one-time OAuth state. The 24-hour app cookie and 10-minute sign-in cookie are Secure and HttpOnly. Private responses are not cacheable. Signing out clears the tab's study progress cache.

Persistent disk survival is not a backup. Keep encrypted backups outside the service and outside any public repository. For an offline backup, stop writes from both the API and worker, then copy the **entire `/var/data` directory**, including any SQLite `-wal` and `-shm` files, media, and checkpoints. Do not copy only live `.sqlite` files while writes continue. For a live database-only backup, use Python's SQLite `Connection.backup()` API for each database; separately coordinate media/checkpoint copies so they match the database snapshot.

Restore while the service is stopped, preserving directory layout and using the same Google client/account subjects. Prefer an application backup over restoring a raw disk snapshot for SQLite. Render's [persistent disk documentation](https://render.com/docs/disks) explains its disk and snapshot limitations. Restoring active sessions can revive unexpired sessions; clear session rows after restoring if that is undesirable. Temporary files may be discarded only with both processes stopped.

## Verification

GitHub's **Hosting checks** workflow runs the backend and interface tests, both frontend builds, and a real Docker build. Its container smoke check verifies FFmpeg, signed-out denial, SQLite/disk persistence across restart, and shutdown when the worker dies using fake credentials. It does not exercise real Google login or charge OpenAI. Those require the live checks above.

The Windows local launcher remains `scripts/start.ps1`; it uses local mode unless explicitly configured otherwise. No OAuth settings are required locally. Docker can also run on another HTTPS host with the same environment and mounted persistent data directory.
